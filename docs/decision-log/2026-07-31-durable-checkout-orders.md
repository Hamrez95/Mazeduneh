# لاگ تصمیم — سفارش و رزرو ماندگار

## مسئله

Checkout اولیه از قیمت سرور، Idempotency و رزرو موجودی پشتیبانی می‌کرد، اما سفارش، کلید Idempotency و رزرو در حافظه فرایند بودند. Restart یا چند Replica می‌توانست سفارش را ناپدید، موجودی را ناهماهنگ و Retry را ناامن کند.

## گزینه‌ها

1. ادامه نگهداری حافظه‌ای تا زمان خرید هاست — رد شد؛ چون رفتار اصلی فروش قابل اعتماد و قابل تست نبود.
2. ذخیره فقط سفارش و نگه‌داشتن موجودی در حافظه — رد شد؛ چون اتمیک‌بودن سفارش و انبار از بین می‌رفت.
3. انتقال سفارش، ردیف‌ها، تاریخچه، Idempotency و رزرو موجودی به یک تراکنش PostgreSQL — انتخاب شد.

## نظر میزگرد

- **مدیر محصول و فروش:** مبلغ پرداختی و زمان انقضای رزرو باید در رسید ثابت بماند.
- **مدیر فنی و Backend:** PostgreSQL مرجع قیمت، موجودی و Idempotency است؛ ردیف Variant با `FOR UPDATE` قفل می‌شود.
- **انباردار:** کاهش موجودی فقط پس از اعتبارسنجی همه ردیف‌ها و در تراکنش all-or-nothing انجام می‌شود.
- **حسابدار:** عنوان کالا، SKU، قیمت واحد و جمع ردیف Snapshot می‌شوند تا تغییرات بعدی کاتالوگ فاکتور قبلی را عوض نکند.
- **امنیت:** Receipt Token تصادفی ۱۹۲ بیتی باقی می‌ماند و مقایسه آن زمان‌ثابت است.
- **QA:** CI باید Retry، Restart و بازیابی سفارش را با PostgreSQL واقعی اثبات کند.
- **UX:** خطاهای کمبود موجودی و تعارض Idempotency فارسی و قابل اقدام باقی می‌مانند.

## تصمیم و پیاده‌سازی

- جداول مستقل برای سفارش، ردیف، Transition و Idempotency ایجاد شد.
- موجودی Variantها هنگام Checkout با قفل ردیف و در همان تراکنش کم می‌شود.
- Retry با همان Payload همان سفارش را برمی‌گرداند و موجودی دوباره کم نمی‌شود.
- استفاده مجدد از کلید برای Payload متفاوت با Conflict متوقف می‌شود.
- Worker هر دقیقه رزروهای ۲۰ دقیقه‌ای منقضی را آزاد و Transition `Expired` ثبت می‌کند.
- در نبود Connection String، حالت حافظه‌ای برای Preview و توسعه ساده حفظ شده، اما فروش واقعی مجاز نیست.
- کش درون‌فرایندی کاتالوگ پس از Commit با موجودی نهایی دیتابیس همگام می‌شود.

## تست و گیت

CI با PostgreSQL 17 باید:

1. API را Build و اجرا کند.
2. سفارش آزمایشی بسازد.
3. همان درخواست را Retry و یکسان‌بودن Order ID را بررسی کند.
4. API را Restart کند.
5. سفارش را با Receipt Token از PostgreSQL بازیابی کند.
6. Build سایت، Flutter Web و APK نیز سبز بمانند.

## ریسک باقی‌مانده

- اتصال درگاه Sandbox و Transition پرداخت هنوز لازم است.
- پنل مدیریت سفارش‌ها و لغو دستی هنوز لازم است.
- Receipt Token فعلاً به‌صورت opaque در دیتابیس ذخیره می‌شود؛ رمزنگاری در حالت سکون به زیرساخت میزبان وابسته است.
- تست آزادسازی رزرو منقضی باید در برش پرداخت/سفارش گسترش یابد.
