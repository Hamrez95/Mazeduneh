# کنترل انتشار محصول — ۱۴۰۵/۰۵/۰۹

## مسئله
مدیر فروشگاه می‌توانست محصول ایجاد کند، اما راه امن و ماندگاری برای خارج‌کردن آن از فروش یا انتشار مجدد وجود نداشت. حذف فیزیکی محصول برای کالایی که ممکن است سابقه سفارش، انبار یا حسابداری داشته باشد انتخاب درستی نیست.

## گزینه‌ها
1. حذف محصول: رد شد؛ تاریخچه و ارجاعات آینده را تهدید می‌کند.
2. نگهداری وضعیت فقط در پنل: رد شد؛ فروشگاه و API حقیقت متفاوت خواهند داشت.
3. وضعیت انتشار در Backend و PostgreSQL: انتخاب شد.

## تصمیم
- فهرست عمومی فقط محصولات منتشرشده را برمی‌گرداند.
- جزئیات عمومی Draft یا محصول خارج‌شده از فروش، پاسخ 404 فارسی می‌دهد.
- مسیر مدیریتی همه محصولات شامل Draftها را برمی‌گرداند.
- تغییر وضعیت با PATCH انجام و در PostgreSQL ذخیره می‌شود.
- تغییر وضعیت idempotent است؛ ارسال دوباره همان مقدار نتیجه ناسازگار ایجاد نمی‌کند.

## معیار پذیرش
- Draft در GET عمومی ظاهر نشود.
- GET جزئیات Draft اطلاعات محصول را افشا نکند.
- مدیر بتواند همه محصولات را ببیند.
- Publish/Unpublish پس از Restart باقی بماند.
- محصول ناموجود پاسخ فارسی 404 بدهد.
- CI کامل API، Storefront و Flutter سبز باشد.

## نظر میزگرد
- محصول و فروش: خروج موقت از فروش باید بدون حذف محصول انجام شود.
- انبار و حسابداری: رکورد کالا برای تاریخچه موجودی و هزینه‌ها حفظ شود.
- متخصص خشکبار: توقف فروش برای محصول منقضی، ناموجود یا مردود کیفی ضروری است.
- امنیت و QA: مسیر مدیریتی در این مرحله قرارداد فنی است و پیش از Production باید پشت احراز هویت و نقش قرار گیرد.
- UI/UX: پنل بعداً باید وضعیت واضح «منتشرشده/پیش‌نویس» و تأیید تغییر نشان دهد.

## ریسک باقی‌مانده
مسیرهای مدیریتی هنوز احراز هویت ندارند؛ تا تکمیل نقش‌ها و Audit Log، API نباید به‌صورت عمومی و Production منتشر شود.
