# لاگ تصمیم — Checkout سمت سرور و رزرو موجودی

## مسئله
قیمت، هزینه ارسال و موجودی نباید به داده ارسالی مرورگر اعتماد کنند. Retry شبکه نیز نباید سفارش یا رزرو تکراری بسازد.

## معیار پذیرش این برش
- قیمت هر ردیف فقط از کاتالوگ منتشرشده خوانده شود.
- هزینه ارسال پیش از پرداخت در پاسخ دیده شود.
- درخواست تکراری با `Idempotency-Key` همان سفارش را برگرداند.
- استفاده همان کلید برای Payload متفاوت با Conflict رد شود.
- موجودی ناکافی، کل سفارش را بدون رزرو ناقص رد کند.
- هر سفارش تاریخ انقضای رزرو و نخستین Transition ثبت‌شده داشته باشد.
- رسید سفارش بدون Receipt Token قابل خواندن نباشد.

## نظر میزگرد
- **محصول و فروش:** مبلغ نهایی باید قبل از انتقال به درگاه شفاف باشد.
- **مدیر فنی و Backend:** Idempotency و قفل داخل Process برای نخستین Vertical Slice پذیرفته شد؛ persistence و قفل دیتابیس گام بعدی است.
- **انبار:** موجودی در سطح بسته قابل فروش رزرو می‌شود، نه وزن خام.
- **حسابداری:** مبلغ‌ها با ریال و Decimal نگهداری می‌شوند؛ تخفیف فعلاً صفر است تا Rule جعلی وارد نشود.
- **QA:** کلید تکراری، Payload متفاوت، SKU ناموجود و موجودی ناکافی Gate هستند.
- **امنیت:** شناسه GUID به‌تنهایی برای دریافت سفارش کافی نیست و Receipt Token جدا لازم است.
- **UI/UX:** پاسخ API شامل Subtotal، Shipping، Discount و Payable است تا Checkout ابهام نداشته باشد.

## تصمیم
یک endpoint عمومی Guest Checkout ساخته شد که Server-owned pricing، Idempotency و رزرو اتمیک حافظه‌ای را فراهم می‌کند. سفارش در حالت `AwaitingPayment` و با مهلت ۲۰ دقیقه ایجاد می‌شود.

## مرز صادقانه
این برش هنوز Production-ready نیست: سفارش، Idempotency و رزرو در حافظه Process هستند و پس از Restart از بین می‌روند. آزادسازی خودکار رزرو، PostgreSQL transaction/row lock، Payment Sandbox و Audit پایدار در برش‌های بعدی انجام می‌شوند.

## ریسک و کنترل
- Oversell بین چند Instance هنوز ممکن است؛ تا انتقال رزرو به PostgreSQL، API نباید چند Replica فروش واقعی داشته باشد.
- اطلاعات نشانی در حافظه است؛ Log نمی‌شود و endpoint رسید به Receipt Token نیاز دارد.
- قیمت Client نادیده گرفته می‌شود و فقط SKU و Quantity پذیرفته می‌شود.
