# لاگ تصمیم — کاتالوگ زنده، سبد و Checkout فروشگاه

## مسئله

فروشگاه از نظر ظاهری آماده بازبینی بود، اما محصول‌ها، انتخاب بسته، سبد و دکمه‌های خرید فقط نمایشی بودند. Backend سفارش امن داشت، ولی مشتری مسیر کاملی برای استفاده از آن نداشت.

## نظر میزگرد

- **محصول و فروش:** مشتری باید وزن/پک، موجودی، جمع سبد، هزینه ارسال و مهلت رزرو را پیش از پرداخت ببیند.
- **Frontend و UX:** سبد باید در موبایل Drawer تمام‌عرض و در دسکتاپ پنل جانبی باشد؛ Cart در مرورگر حفظ شود.
- **Backend و امنیت:** قیمت Client فقط تخمینی است و مبلغ قطعی باید از Endpoint Checkout برگردد؛ برای هر ارسال کلید Idempotency مستقل تولید می‌شود.
- **QA:** سایت باید هم با API زنده و هم در Static Preview بدون شکست Build شود.
- **بازاریابی:** حالت Preview نباید به‌اشتباه فروش واقعی تلقی شود؛ وضعیت اتصال باید واضح باشد.
- **انبار و حسابداری:** موجودی و مبلغ نمایش‌داده‌شده از Variant می‌آیند، اما رزرو و مبلغ قطعی فقط در سرور معتبرند.

## تصمیم

- کاتالوگ در Runtime از `NEXT_PUBLIC_MAZEDUNEH_API_BASE_URL` خوانده می‌شود.
- در نبود یا خرابی API، داده نمونه با برچسب صریح Preview نمایش داده می‌شود.
- انتخاب Variant، افزودن، کاهش/افزایش تعداد و ذخیره Cart در Local Storage پیاده شد.
- فرم Checkout اطلاعات تحویل را همراه SKU و تعداد به Backend ارسال می‌کند.
- قیمت یا جمع محاسبه‌شده Client به Backend ارسال نمی‌شود.
- پاسخ موفق، شماره سفارش، وضعیت، مبلغ قطعی و زمان انقضای رزرو را نمایش می‌دهد.
- پرداخت واقعی عمداً غیرفعال و داخل رسید اعلام شده است.

## گیت تست

- TypeScript بدون خطا
- Next.js Production Build و Static Export
- API و Flutter نباید Regression داشته باشند
- حالت API unset باید Build شود
- حالت خطای API باید بدون Crash به Preview برگردد

## ریسک باقی‌مانده

- تست مرورگر E2E برای Cart و Checkout باید اضافه شود.
- API و PostgreSQL عمومی هنوز استقرار نیافته‌اند.
- صفحه جزئیات محصول، تصویر واقعی، جست‌وجو و فیلتر پیشرفته در برش‌های بعدی تکمیل می‌شوند.
- پرداخت Sandbox و Callback هنوز لازم است.
