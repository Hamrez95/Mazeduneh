# دفتر تصمیم — ورود مالک در پنل Flutter

## مسئله

پس از محافظت API، پنل Flutter هنوز صفحه ورود و Bearer Token نداشت. انتشار همان پنل باعث خطای دائمی 401 می‌شد.

## گزینه‌ها

1. ذخیره Token در localStorage یا SharedPreferences: برای برش اولیه رد شد؛ زیرا ماندگاری Token روی دستگاه عمومی ریسک سرقت نشست را افزایش می‌دهد.
2. API Key دائمی داخل Build: رد شد؛ Secret از APK و Web قابل استخراج است.
3. Access Token کوتاه‌عمر در حافظه: انتخاب شد؛ کم‌هزینه، قابل تست و مناسب مرحله Owner-only است.

## تصمیم

- ورود از Endpoint رسمی مالک انجام می‌شود.
- Token فقط در حافظه فرایند نگهداری می‌شود.
- تمام درخواست‌های مدیریتی Authorization Header دارند.
- پاسخ 401 Session را پاک می‌کند و Auth Gate صفحه ورود را نمایش می‌دهد.
- Buildهای CI از entrypoint امن `lib/secure_main.dart` تولید می‌شوند.

## معیار پذیرش

- Login موفق Session معتبر بسازد.
- Password یا Token در سورس، URL و Log ثبت نشود.
- درخواست مدیریتی بدون Token اجرا نشود.
- 401 موجب Logout شود.
- 429 پیام فارسی غیرحساس داشته باشد.
- Flutter Analyze، Test، Web و Android Build سبز شوند.

## نقد میزگرد

- محصول و فروش: ورود مالک پیش‌شرط انتشار پنل متصل است.
- مدیر فنی و Backend: Token کوتاه‌عمر بهتر از API Key دائمی است.
- Flutter: Auth Gate و Session از Catalog Client جدا بمانند.
- UI/UX: خطا به‌صورت live region و بدون افشای علت دقیق اعتبارنامه نمایش داده شود.
- QA: Login، Bearer Header، 401 و 429 تست شوند.
- حسابداری، انبار و متخصص خشکبار: در آینده Roleهای مستقل و Audit Log دائمی لازم است.
- بازاریابی و گرافیک: هویت بصری سبز/کرم در صفحه ورود حفظ شود، بدون قربانی‌کردن خوانایی.

## ریسک باقی‌مانده

- Session با بسته‌شدن یا Refresh اپ از بین می‌رود؛ برای مرحله اولیه آگاهانه پذیرفته شد.
- Refresh Token، MFA، Secure Storage و Role Matrix هنوز پیاده‌سازی نشده‌اند.
- API و دیتابیس عمومی تا تنظیم Secrets معتبر منتشر نمی‌شوند.
