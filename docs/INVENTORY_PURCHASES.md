# Dated inventory purchases

Admin → انبار → ثبت خرید. Select the sellable SKU/package, enter the unique receipt/batch code, package quantity, purchase date, supplier (optional), production/expiry and per-package purchase/packaging/additional costs. UI money is toman; API values are rial. Purchase totals exclude packaging/additional and equal unit purchase cost × received package count. Dates are explicitly Gregorian with Persian digits; a date picker is available. This receipt is for packaged SKU units, not bulk kilograms or raw-material stock conversion.

Successful receipt returns to the inventory list with a confirmation and refreshed balance/history. Failed receipt keeps the draft for correction/retry; submit is disabled while pending. Duplicate SKU/batch returns 409 without adding stock twice. Inventory-write is required; read-only users cannot submit. The existing history shows date, supplier, received quantity, unit cost and total; legacy rows keep unknown purchase dates rather than inventing them. Catalog sale prices do not change on receipt.

POST `/api/v1/admin/inventory/batches` adds optional `purchasedAt` (ISO timestamp, not future) and `supplier` (≤200 characters). Existing requests remain valid and default new purchase date to server receipt time. GET includes those fields and `purchaseTotal`. Migration inventory/003-purchase-history is additive and repeat-safe; old receipts remain unchanged. Logical rollback deploys the old API while leaving nullable columns and index intact. Stock, receipt and audit are one PostgreSQL transaction. Audit uses the authenticated actor, request ID, timestamp, null before and the complete new receipt after. Ledger uses the same actor.

Customer catalog projections zero internal cost fields; authenticated Admin retains actual costs. Existing JSON shape stays compatible. Storefront price, order cost snapshots and tax calculation are otherwise unchanged. Single-store API/database architecture is retained; cross-store isolation remains #99. The database is not exposed directly to browsers. For a Supabase deployment, keep these API-managed tables inaccessible to public Data API roles and verify policies before provisioning.
